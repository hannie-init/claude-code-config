# QA Ticket 자동 처리 워크플로우

인수: $ARGUMENTS

---

## 입력 검증 규칙 (전역 — 모든 Phase에 적용)

아래 검증 규칙은 외부 입력이 사용되는 모든 지점에서 반드시 적용합니다.
검증 실패 시 즉시 실행을 중단하고 사용자에게 오류 내용을 출력합니다.

| 입력 | 허용 패턴 | 거부 조건 |
|------|-----------|-----------|
| PROJECT_KEY | `^[A-Z][A-Z0-9_]{1,9}$` | 특수문자, 소문자, 빈 문자열 |
| 브랜치명 | `^[a-zA-Z0-9/_.-]{1,255}$` | 공백, `;`, `$`, `\``, `(`, `)`, `&`, `|` 등 쉘 메타문자 |
| 레포 경로 | 절대 경로 + `realpath` 정규화 후 허용 workspace prefix 내부 | `..` 포함, 허용 prefix 외부 경로 |
| Figma URL | `^https://(www\.)?figma\.com/` | http, localhost, IP 주소, 내부망 주소 |
| Jira 티켓 ID | `^[A-Z][A-Z0-9_]+-[0-9]+$` | 위 형식에 맞지 않는 모든 값 |

## 준비 단계

### 1. MCP 도구 로드

ToolSearch로 Atlassian과 Figma MCP 도구 스키마를 로드합니다.

```
ToolSearch: "select:mcp__claude_ai_Atlassian__authenticate"
ToolSearch: "select:mcp__claude_ai_Figma__authenticate,mcp__claude_ai_Figma__whoami,mcp__claude_ai_Figma__get_design_context,mcp__claude_ai_Figma__get_screenshot,mcp__claude_ai_Figma__get_metadata"
```

이후 ToolSearch로 사용 가능한 Atlassian 도구 전체를 탐색합니다:

```
ToolSearch: "atlassian jira issue search transition comment"
```

### 2. 인증 확인

**Atlassian MCP:** `whoami` 또는 현재 사용자 조회로 인증 상태를 확인합니다.
- 미인증 → `mcp__claude_ai_Atlassian__authenticate` 실행 후 계속

**Figma MCP:** `mcp__claude_ai_Figma__whoami`로 인증 상태를 확인합니다.
- 미인증 → `mcp__claude_ai_Figma__authenticate` 실행 후 계속

## Phase 1: Jira 티켓 조회

**PROJECT_KEY 검증:** `--project` 인수가 있으면 반드시 `^[A-Z][A-Z0-9_]{1,9}$` 패턴 검증 후 사용합니다.
검증 실패 시 실행을 중단하고 "유효하지 않은 PROJECT_KEY 형식입니다." 메시지를 출력합니다.

Atlassian MCP로 나에게 할당된 QA 티켓을 조회합니다.

JQL (파라미터는 반드시 검증된 값만 사용):
```
assignee = currentUser() AND issuetype = QA ORDER BY created DESC
```

`--project` 인수가 있으면 `project = {VALIDATED_PROJECT_KEY} AND` 조건을 앞에 추가합니다.

결과를 아래 형식으로 출력합니다:

```
=================================================
[ QA 티켓 목록 ]

📋 BACKLOG
  [PROJ-101] 로그인 페이지에서 비밀번호 오류 메시지 미표시
  [PROJ-105] 검색 결과 0건일 때 빈 화면 표시

⚙️  개발하기로 선택 (진행 중)
  [PROJ-098] 회원가입 이메일 중복 체크 오작동

✅ RESOLVED (최근 5건)
  [PROJ-095] ...
=================================================
```

## Phase 2: 진행할 티켓 선택

사용자에게 진행할 BACKLOG 티켓 ID를 입력받습니다.

```
진행할 티켓 ID를 입력하세요 (예: PROJ-101):
```

**티켓 ID 검증:** 입력값을 `^[A-Z][A-Z0-9_]+-[0-9]+$` 패턴으로 검증합니다.
검증 실패 시 "유효하지 않은 티켓 ID 형식입니다." 를 출력하고 재입력을 요청합니다.

입력받은 티켓 ID로 상세 내용을 조회합니다.

**⚠️ 중요:** 이 단계에서는 Jira 상태를 변경하지 않습니다. 상태 변경은 Phase 7(코드 수정 시작 직전)에 수행합니다. 이는 사용자가 Phase 2~6 사이에 작업을 포기하더라도 티켓이 '개발하기로 선택' 상태로 stuck되는 것을 방지합니다.

## Phase 3: 티켓 분석 + 분류 + 사용자 확인

### 3-1. 티켓 내용 분석

티켓의 다음 항목을 추출합니다 (최소 필요 필드만 저장하고 전체 원문은 저장하지 않습니다):
- 제목, 설명 요약, 재현 단계(Steps to Reproduce)
- 기대 동작 vs 실제 동작
- Figma URL (첨부 파일/설명에서 추출)
- 우선순위, 환경 정보

**⚠️ 보안:** 티켓 원문을 파일로 저장하지 않습니다. PII, 인증 토큰, 내부 시스템 정보가 포함될 수 있습니다. 이후 단계에 필요한 최소 필드만 변수로 유지합니다.

### 3-2. 분류 판단

티켓 내용을 분석해 아래 중 하나로 분류합니다:

| 분류 | 기준 |
|------|------|
| UI/UX | 화면 표시, 레이아웃, 인터랙션, 문구 관련 |
| 로직/API | 비즈니스 로직 오류, API 응답 오류, 데이터 처리 |
| 성능 | 응답 지연, 메모리 누수, 타임아웃 |
| 복합 | 위 항목이 둘 이상 해당 |

### 3-3. 분류 결과 출력 및 사용자 확인

아래 형식으로 출력한 뒤 사용자 확인을 받습니다:

```
=================================================
[ 티켓 분석 결과 ]

티켓: [PROJ-101] 로그인 페이지에서 비밀번호 오류 메시지 미표시
분류: UI/UX

재현 시나리오:
  1. 로그인 페이지 진입
  2. 잘못된 비밀번호 입력 후 로그인 시도
  3. 오류 메시지가 표시되어야 하나 화면 변화 없음

기대 동작: "비밀번호가 올바르지 않습니다." 메시지 표시
실제 동작: 메시지 미표시, 폼 초기화만 발생

=================================================
분류가 맞으면 Enter, 수정할 내용이 있으면 입력하세요:
```

### 3-4. Figma 시나리오 분석

**모든 티켓에 대해 Figma 분석을 진행합니다** (UI뿐 아니라 로직/성능 버그도 플로우 확인 목적).

#### Figma URL 확인 및 검증

1. 티켓 첨부 또는 설명에서 Figma URL을 자동 추출합니다.
2. **URL 보안 검증:** 추출된 URL이 반드시 `^https://(www\.)?figma\.com/` 패턴과 일치하는지 확인합니다.
   - 불일치(http, localhost, IP 주소, 내부망 주소 등) → 해당 URL을 폐기하고 사용자에게 유효한 Figma URL을 요청합니다.
   - URL이 없으면 사용자에게 요청합니다:
     ```
     Figma URL을 입력해주세요 (없으면 Enter로 건너뜁니다):
     ```
3. URL이 있으면 `node-id` 파라미터 포함 여부를 확인합니다:
   - `node-id` 있음 → Remote MCP 접근 시도
   - `node-id` 없음 → 아래 안내 출력:
     ```
     ⚠️  파일 전체 URL이 감지되었습니다. 특정 프레임 URL을 입력해주세요.
     (Figma에서 해당 프레임을 선택 → 우클릭 → "Copy link to selection")
     ```

#### Remote MCP 접근 시도

`mcp__claude_ai_Figma__get_design_context`와 `mcp__claude_ai_Figma__get_screenshot`으로 해당 프레임을 fetch합니다.

**Figma 응답 검증 (보안):** 응답 데이터를 코드 생성이나 디버깅 컨텍스트로 활용하기 전에 아래를 확인합니다:
- 응답에 `document`, `name`, `version` 등 기본 Figma 스키마 필드가 포함되어 있는지 확인
- 응답 크기가 합리적 범위인지 확인 (비정상적으로 큰 응답은 경고 후 요약만 사용)
- 응답 내용을 신뢰할 수 없는 외부 데이터로 취급하고 직접 코드에 삽입하지 않음

**성공 시:** 아래 항목을 분석합니다:
- 관련 화면 레이아웃 및 컴포넌트 구조
- 화면 전환 플로우 및 분기 조건
- 에러 상태, 엣지 케이스 화면

**실패 시 (인증 오류, 권한 오류 등):** Desktop MCP로 fallback합니다:
```
⚠️  Remote MCP 접근 실패: {오류 내용}
Figma 데스크톱 앱에서 아래 URL을 열어주세요:
{figma_url}

열었으면 Enter를 누르세요:
```
사용자 확인 후 Desktop MCP (`use_figma` 계열 도구)로 현재 열린 파일을 읽습니다.

#### Figma 분석 결과 요약

```
[ Figma 시나리오 분석 ]

관련 화면: 로그인 화면 (Login / Error State 프레임)
플로우:
  - 정상 로그인 → 홈 화면으로 이동
  - 비밀번호 오류 → Error State 프레임 표시 (설계상 인라인 메시지 노출)
  - 5회 실패 → 계정 잠금 안내 화면

설계 vs 버그:
  설계: Error State 프레임에 인라인 에러 메시지 컴포넌트 존재
  버그: 에러 상태 전환이 발생하지 않음 → 코드에서 에러 핸들링 누락 추정
```

## Phase 4: 디버깅 대상 입력

사용자에게 서버 레포 경로와 브랜치를 입력받습니다:

```
레포지토리 경로를 입력하세요 (예: /Users/hannah/my-project):
```

**레포 경로 검증:**
1. `realpath`로 정규화된 절대 경로를 구합니다.
2. 정규화된 경로가 미리 정의된 workspace prefix (예: `/Users/hannah/`, `/home/`) 내부인지 확인합니다.
3. 검증 실패 시 실행을 중단합니다:
   ```bash
   # 경로 검증 예시
   REAL_PATH=$(realpath "{user_input_path}" 2>/dev/null)
   if [[ "$REAL_PATH" != /Users/hannah/* ]]; then
     echo "⚠️  허용되지 않은 경로입니다. workspace 내부 경로를 입력해주세요."; exit 1
   fi
   ```

```
작업 브랜치를 입력하세요 (현재 브랜치 사용은 Enter):
```

**브랜치명 검증:** 입력값을 `^[a-zA-Z0-9/_.-]{1,255}$` 패턴으로 검증합니다.
쉘 메타문자(`;`, `$`, `` ` ``, `(`, `)`, `&`, `|`, `\n`, 공백 등) 포함 시 실행을 중단합니다.

**Working tree 확인:**
```bash
git -C "{VALIDATED_REPO_PATH}" status --porcelain
```
출력이 비어있지 않으면 (uncommitted/untracked changes 존재) 실행을 중단합니다:
```
⚠️  작업 트리에 미커밋 변경사항이 있습니다.
    변경사항을 stash하거나 commit한 후 다시 시도해주세요.
    (git stash 또는 git commit -m "WIP")
```

**브랜치 전환:**
브랜치 입력이 있으면 검증된 브랜치명으로 checkout합니다:
```bash
git -C "{VALIDATED_REPO_PATH}" checkout -- "{VALIDATED_BRANCH}"
```
입력이 없으면 현재 브랜치를 확인하고 출력합니다.

## Phase 5: 디버깅

### 5-1. 관련 코드 탐색

Agent(subagent_type: Explore)를 사용해 재현 시나리오와 관련된 코드를 탐색합니다.

**탐색 범위 제한:** 탐색 범위를 티켓 분류와 재현 경로 기반으로 좁힙니다:
- 탐색 시작 디렉토리: 티켓 유형에 맞는 관련 모듈 디렉토리 (예: `src/auth/`, `src/api/`)
- 최대 탐색 파일 수: 20개 (초과 시 가장 관련도 높은 20개를 선택)
- 파일 크기 제한: 단일 파일 50KB 초과 시 해당 파일은 Skip하고 파일명만 기록
- 바이너리/minified 파일: 탐색 목록에서 제외

탐색 목표:
- 에러 핸들링 로직이 있는 파일
- 티켓의 재현 경로와 관련된 컨트롤러/서비스/컴포넌트
- API 엔드포인트 또는 상태 관리 코드

### 5-2. 루트 코즈 분석

탐색된 파일들을 Read 도구로 읽어 분석합니다:
- 재현 단계를 코드 레벨로 추적
- 기대 동작과 실제 동작의 분기점 특정
- 영향 범위 (이 버그가 영향을 줄 수 있는 다른 경로) 파악

- `Y` 또는 Enter → Phase 7 진행

## Phase 7: Jira 상태 변경 + 코드 수정 + 검증

### 7-0. Jira 상태 전환 (코드 수정 직전)

**사용 가능한 Transition 조회:** Jira Transitions API로 현재 티켓에서 이동 가능한 상태 목록과 ID를 조회합니다:
```
GET /rest/api/3/issue/{ticket_id}/transitions
```

조회 결과에서 '개발하기로 선택'에 해당하는 transition ID를 찾습니다.
- 해당 이름의 transition이 없으면: "사용 가능한 상태 목록: {목록}" 을 출력하고 사용자에게 정확한 상태명을 입력받습니다.
- 해당 transition 실행 (ID 기반으로 호출, 이름 문자열 직접 사용 금지)

```
✅ [PROJ-101] 상태 변경 완료: BACKLOG → 개발하기로 선택
```

### 7-1. Working Tree 스냅샷 (롤백 준비)

코드 수정 전 반드시 현재 상태를 저장합니다:
```bash
git -C "{VALIDATED_REPO_PATH}" stash push -m "qa-ticket-{ticket_id}-pre-fix"
# stash 참조 ID를 STASH_REF 변수에 저장
STASH_REF=$(git -C "{VALIDATED_REPO_PATH}" stash list | head -1 | cut -d: -f1)
```

### 7-2. 베이스라인 빌드 확인

**코드를 수정하기 전에** 현재 상태의 빌드가 정상인지 확인합니다:

빌드 도구 감지 (레포 루트에서 우선순위 순으로 탐색):
1. `Makefile` → `make build`
2. `pom.xml` → `mvn compile -q`
3. `build.gradle` → `./gradlew compileJava -q`
4. `package.json` → `npm run build` 또는 `yarn build`

베이스라인 빌드 실패 시: 수정을 중단하고 사용자에게 알립니다:
```
⚠️  베이스라인 빌드 실패 — 티켓과 무관한 기존 빌드 오류가 있습니다.
    수정을 진행하면 관련 없는 오류를 수정하게 될 수 있습니다.
    베이스라인 빌드를 먼저 수정한 후 다시 시도해주세요.
```

베이스라인 빌드 성공 시 → 7-3으로 진행

### 7-3. 코드 수정

수정 계획에 따라 Edit/Write 도구로 코드를 수정합니다.
- 수정 범위는 Phase 6에서 확정된 파일에 한정합니다
- 수정 외 코드는 변경하지 않습니다
- 수정된 파일 목록과 변경 내용 요약을 출력합니다

**⚠️ 보안:** 코드에 Figma 응답 데이터를 직접 삽입하지 않습니다. Figma 분석 결과는 코드 수정 방향 결정에만 활용합니다.

### 7-4. 컴파일 / 빌드 확인

7-2와 동일한 빌드 명령으로 수정 후 빌드를 실행합니다.

빌드 실패 시 최대 3회 재시도합니다:
```
재시도 1/3: 오류 분석 후 수정 적용 → 빌드 재실행
재시도 2/3: 오류 분석 후 수정 적용 → 빌드 재실행
재시도 3/3: 오류 분석 후 수정 적용 → 빌드 재실행
```

**3회 재시도 후에도 실패 시:** 자동 수정을 중단하고 사용자에게 보고합니다:
```
⚠️  빌드 수정 3회 시도 후 실패했습니다.
오류 내용: {마지막 빌드 오류}
변경 파일: {수정한 파일 목록}

자동 수정을 중단합니다. 롤백하시겠습니까? (Y/n):
```
- `Y` 또는 Enter → `git stash pop {STASH_REF}` 실행하여 원상 복구

### 7-5. 관련 테스트 실행

수정된 파일과 관련된 기존 테스트를 탐색하고 실행합니다.

테스트 실패가 버그 수정으로 인한 정상적인 변화라면 테스트도 함께 수정합니다.
예상치 못한 실패라면 사용자에게 보고하고 확인을 받습니다:
```
⚠️  예상치 못한 테스트 실패:
{실패한 테스트 이름}: {실패 메시지}

이 실패가 수정과 관련 없다면 별도로 처리할 수 있습니다.
계속 진행하시겠습니까? (Y/n):
```

## Phase 8: 코드 리뷰 진행 여부

```
=================================================
코드 수정 및 검증이 완료되었습니다.

수정 파일:
  - src/auth/LoginController.java
  - src/auth/LoginControllerTest.java

빌드: ✅ 성공
테스트: ✅ 14/14 통과

코드 리뷰를 진행할까요? (Y/n):
=================================================
```

- `Y` 또는 Enter → 아래 방식으로 코드 리뷰를 진행합니다:
  1. `git diff HEAD` 로 변경된 hunks만 추출합니다
  2. 수정된 파일들에 대해 `/review` 스킬을 **병렬로 동시에** 실행합니다 (단일 메시지에서 Agent 도구를 수정 파일 수만큼 동시 호출)
  3. 리뷰 입력은 전체 파일이 아닌 **git diff 결과**를 사용합니다 (기존 코드의 pre-existing 이슈가 새 이슈로 오인되는 것 방지)
- `n` → Phase 9로 진행합니다

## Phase 9: Jira 마무리

### 9-1. 티켓 상태 변경

**사용 가능한 Transition 재조회:** Jira Transitions API로 현재 티켓에서 이동 가능한 상태 목록을 다시 조회합니다.
'RESOLVED'에 해당하는 transition ID를 찾아 ID 기반으로 호출합니다.

Transition 실패 시: 자동으로 종료하지 않고 사용자에게 알립니다:
```
⚠️  Jira 상태 변경 실패: {오류 내용}

코드 수정은 완료되었으나 Jira 티켓 상태가 변경되지 않았습니다.
아래 URL에서 수동으로 상태를 변경해주세요:
https://your-jira.atlassian.net/browse/{ticket_id}

목표 상태: RESOLVED (또는 해당 프로젝트의 완료 상태)
```

### 9-2. 코멘트 추가

아래 내용을 Jira 티켓 코멘트로 추가합니다:

```
[자동 처리 완료]

■ 루트 코즈
{루트 코즈 요약 — 2-3줄}

■ 수정 파일
- {수정된 파일 목록}

■ 검증 결과
- 빌드: 성공
- 테스트: {통과 건수}/{전체 건수}
{코드 리뷰를 진행한 경우: - 코드 리뷰: 완료 (채택 이슈 N건 수정)}

■ Figma 시나리오 참조
{분석한 Figma 프레임 URL}
```

코멘트 추가 실패 시: 콘솔에 내용을 출력하고 수동으로 추가할 수 있도록 안내합니다.

### 9-3. 완료 출력

```
=================================================
✅ QA 티켓 처리 완료

티켓: [PROJ-101] 로그인 페이지에서 비밀번호 오류 메시지 미표시
상태: RESOLVED
수정 파일: src/auth/LoginController.java, src/auth/LoginControllerTest.java
리포트: Jira 티켓 코멘트에 기록 완료
=================================================
```
