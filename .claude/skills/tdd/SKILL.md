# TDD 개발 프로세스

입력: $ARGUMENTS (예: "사용자 포인트 적립 기능" 또는 docs/features/point/spec.md)

아래 단계를 순서대로 진행한다.  
**각 단계가 끝날 때마다 반드시 사용자 확인을 받고 다음 단계로 넘어간다.**

---

## 1단계: 요구사항 인터뷰

$ARGUMENTS로 받은 기능 설명을 기반으로, 아래 관점에서 빠진 정보를 질문한다.  
한 번에 3개 이하의 질문만 한다. 답변을 받으면 추가 질문이 필요한지 판단하고 반복한다.

**질문 관점:**
- **Actor** — 이 기능을 호출하는 주체는 누구인가? (사용자, 관리자, 스케줄러 등)
- **Trigger** — 어떤 조건/이벤트에서 실행되는가?
- **Input** — 어떤 데이터를 받는가? 필수/선택 구분, 형식 제약
- **Output** — 성공 시 무엇을 반환하거나 변경하는가?
- **비즈니스 규칙** — 중복 처리, 한도, 순서, 우선순위 등 특수 규칙
- **예외 상황** — 잘못된 입력, 존재하지 않는 리소스, 권한 부족, 외부 시스템 장애
- **연관 기능** — 영향을 주거나 받는 다른 기능이 있는가?

인터뷰가 충분하다고 판단되면 아래 형식으로 요구사항 요약을 출력하고 사용자 승인을 요청한다.

```
## 요구사항 요약

**기능명**: ...
**Actor**: ...
**Trigger**: ...
**Input**: ...
**Output**: ...
**비즈니스 규칙**:
  - ...
**예외 상황**:
  - ...

이 내용이 맞으면 "확인"을 입력해 주세요. 수정할 부분이 있으면 알려주세요.
```

---

## 2단계: 인수 조건 도출

승인된 요구사항을 기반으로 Given/When/Then 형식의 인수 조건을 작성한다.

**출력 형식:**
```
## 인수 조건

### AC-01: [조건명]
- Given: ...
- When: ...
- Then: ...

### AC-02: [조건명]
- Given: ...
- When: ...
- Then: ...
```

인수 조건을 출력한 후 사용자 확인을 요청한다.  
"추가", "수정", "삭제" 요청을 반영하고 재출력한다.

---

## 3단계: 테스트 케이스 설계

확정된 인수 조건을 기반으로 테스트 케이스 목록을 작성한다.  
**정상(Happy Path) / 예외(Exception) / 경계값(Boundary)** 세 카테고리로 분류한다.

**출력 형식:**
```
## 테스트 케이스 목록

### [Service 단위 테스트] {ServiceName}Test

**정상 케이스**
| # | 테스트명 | 시나리오 | 기댓값 |
|---|---------|---------|--------|
| S-01 | ... | ... | ... |

**예외 케이스**
| # | 테스트명 | 시나리오 | 기댓값 |
|---|---------|---------|--------|
| E-01 | ... | ... | ... |

**경계값 케이스**
| # | 테스트명 | 시나리오 | 기댓값 |
|---|---------|---------|--------|
| B-01 | ... | ... | ... |

### [Controller 슬라이스 테스트] {ControllerName}Test
...
```

테스트 케이스 목록을 출력한 후 사용자 확인을 요청한다.  
추가/수정/삭제 요청을 반영하고 재출력한다.

---

## 4단계: 테스트 코드 작성

[test-writer 서브에이전트 호출]

입력으로 전달:
- 2단계 인수 조건 전문
- 3단계 테스트 케이스 목록 전문
- 프로젝트의 기존 테스트 파일 경로 (패턴 파악용, src/test/java/ 하위)

test-writer는 아래 규칙으로 테스트 코드를 작성한다:

**Service 단위 테스트**
- `@ExtendWith(MockitoExtension.class)`
- 의존성은 `@Mock`, 테스트 대상은 `@InjectMocks`
- 메서드명: `테스트케이스번호_시나리오_기댓값` (예: `S01_유효한요청_포인트적립성공`)
- 현재 구현 코드가 없으므로 Service 클래스와 메서드 시그니처는 인수 조건에서 추론해 선언
- 테스트 본문은 완성하되, 구현 클래스가 없어 컴파일 안 됨은 정상

**Controller 슬라이스 테스트**
- `@WebMvcTest({ControllerName}.class)`
- `MockMvc` 사용, 요청/응답 JSON 검증
- 인증이 필요한 경우 `@WithMockUser` 또는 Security 설정 무효화

완료 후 출력:
- 작성된 테스트 파일 경로 목록
- 총 테스트 케이스 수
- 구현 시 반드시 맞춰야 할 인터페이스 목록 (클래스명, 메서드 시그니처)

---

## 5단계: 구현 안내

사용자에게 아래 메시지를 출력한다:

```
## 구현 단계

테스트 코드가 준비됐습니다. 이제 구현 코드를 작성할 차례입니다.

**구현이 필요한 인터페이스:**
{4단계에서 출력한 인터페이스 목록}

구현이 완료되면 "검증해줘"라고 입력해 주세요.
```

---

## 6단계: 빌드 및 테스트 검증

사용자가 "검증해줘"를 입력하면 실행한다.

[validator 서브에이전트 호출]
- `./gradlew clean compileJava` 실행
- `./gradlew test` 실행
- **성공 시**: "모든 테스트 통과 ✅" 출력
- **실패 시**: 실패 원인을 분석하고 아래 중 하나를 수행

**컴파일 에러 (최대 3회)**
- 에러가 테스트 코드(`src/test/`)에 있으면: [test-writer] 호출해 수정
- 에러가 구현 코드(`src/main/`)에 있으면: 에러 내용을 사용자에게 보고하고 수정 요청

**테스트 실패 (최대 2회)**
- [test-writer] 호출해 원인 분석
  - 테스트 코드 문제: 수정 후 재검증
  - 구현 로직 문제: 사용자에게 보고하고 수정 요청

한계 초과 시:
```
⛔ 자동 수정 한계 도달

{최종 에러 메시지 전문}

위 내용을 확인 후 직접 수정해 주세요.
```
